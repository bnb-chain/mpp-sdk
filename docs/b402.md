# b402 (Binance OnchainPay) — minimal integration

**TL;DR:** this package exposes two explicit integration modes against the
hosted Binance b402 facilitator. MPP `authorization` credentials can delegate
only their settlement step to b402; standalone x402 resources use B402 Exact
with `eip3009` and/or `permit2-exact`. The SDK is not a facilitator or an order
system.

> ⚠️ **Mainnet only today.** The b402 testnet facilitator's eip3009 kind
> advertises an EIP-712 domain name (`"U"`) that matches no known testnet
> `$U` contract, so testnet authorization settles currently fail upstream
> ([adr/0004](adr/0004-b402-permit2.md) open question 2). `bsc` = real funds —
> keep the per-request price small. (Testnet IS usable for the
> [Permit2 extension](#extension--permit2-on-the-standalone-x402-wire) below.)

## Server — complete and runnable

Prerequisite: Binance OnchainPay **merchant onboarding** (no self-serve
signup) — it issues the credentials below and registers your **payout
address** per chain.

Project setup + `.env`:

```bash
pnpm add @bnb-chain/mpp mppx viem hono @hono/node-server && pnpm add -D tsx
```

```bash
# .env
RECIPIENT_ADDRESS=0x...                   # your REGISTERED b402 payout — b402 settles to it
MPP_SECRET_KEY=...                        # openssl rand -hex 32 (challenge-binding HMAC)
B402_CHAIN=bsc                            # explicit, required (see the warning above)
B402_BASE_URL=https://cb.binanceapi.com   # mainnet facilitator
B402_CLIENT_ID=...
B402_ACCESS_TOKEN=...
B402_PRIVATE_KEY=...                      # the RSA key from onboarding (Base64 PKCS#8
                                          # DER / Base64-PEM / raw PEM — NOT a 0x EVM key)
```

`server.ts` — the whole file, run with
`node --env-file=.env --import tsx server.ts`:

```ts
import { chargeFromDecimal } from '@bnb-chain/mpp'
import { createB402Extension } from '@bnb-chain/mpp/b402/mppx'
import { B402Client } from '@bnb-chain/mpp/b402/server'
import { chargeAsync } from '@bnb-chain/mpp/server'
import { serve } from '@hono/node-server'
import { Hono } from 'hono'
import { Mppx } from 'mppx/server'

const client = B402Client.fromEnv() // reads the B402_* vars; a partial config throws
if (!client) throw new Error('b402 not configured — set the B402_* vars in .env')
const b402 = createB402Extension({
  client,
  methods: ['eip3009', 'permit2-exact'],
})

const charge = await chargeAsync(
  b402.chargeParams({
    chain: 'bsc', // ← keep in sync with B402_CHAIN
    recipient: process.env.RECIPIENT_ADDRESS as `0x${string}`,
  }),
)
const handler = Mppx.create({ methods: [charge], secretKey: process.env.MPP_SECRET_KEY! })

// 0.01 $U per request ($U has 18 decimals) — atomic units on the wire.
const PRICE = chargeFromDecimal({ amount: '0.01', decimals: 18 }).amount

const app = new Hono()
app.get('/api/premium', async (c) => {
  const result = await handler.evm.charge({ amount: PRICE })(c.req.raw)
  if (result.status === 402) return result.challenge // 402 + WWW-Authenticate: Payment
  // Paid + settled by b402 — attach the Payment-Receipt header.
  return result.withReceipt(c.json({ report: 'premium content', at: new Date().toISOString() }))
})

serve({ fetch: app.fetch, port: Number(process.env.PORT ?? 3001) }, (i) => {
  console.log(`listening on :${i.port} — try: curl -i http://localhost:${i.port}/api/premium`)
})
```

## Buyer — complete and runnable

The buyer speaks the plain mpp wire — nothing b402-specific reaches it. It
needs the payer's key and **zero gas** (sign-only; b402 broadcasts). The
wallet must hold mainnet `$U`.

`buyer.ts` — the whole file, run with
`PAYER_PRIVATE_KEY=0x... node --import tsx buyer.ts [url]`:

```ts
import { deserializeEvmReceipt } from '@bnb-chain/mpp'
import { createAuthorizationCredential } from '@bnb-chain/mpp/client'
import { Challenge } from 'mppx'
import { privateKeyToAccount } from 'viem/accounts'

const url = process.argv[2] ?? 'http://localhost:3001/api/premium'
const payer = privateKeyToAccount(process.env.PAYER_PRIVATE_KEY as `0x${string}`)

// 1. Probe — expect 402 + a WWW-Authenticate: Payment challenge.
const probe = await fetch(url)
if (probe.status !== 402) throw new Error(`expected 402, got ${probe.status}`)
// Drain the unused body: Node's fetch (undici) keeps the pooled connection
// busy until the body is consumed, which can stall the paid retry below.
await probe.body?.cancel()
const challenge = Challenge.deserialize(probe.headers.get('WWW-Authenticate')!)

// 2. Read EVERY signing input off the challenge — never hard-code amounts.
const req = challenge.request as {
  amount: string
  currency: `0x${string}`
  recipient: `0x${string}`
  methodDetails: { chainId: number; credentialTypes?: string[] }
}
if (!req.methodDetails.credentialTypes?.includes('authorization')) {
  throw new Error(
    `server does not accept 'authorization' (offers: ${req.methodDetails.credentialTypes})`,
  )
}

// 3. Sign the EIP-3009 authorization — zero gas, nothing broadcast here.
//    The token's EIP-712 domain is a property of the CONTRACT, not the wire
//    (rule 4 below): mainnet $U is name "United Stables", version "1".
const credential = await createAuthorizationCredential({
  challenge,
  account: payer, // any viem LocalAccount; browser wallets: see the note below
  chainId: req.methodDetails.chainId,
  currency: req.currency,
  recipient: req.recipient,
  amount: req.amount,
  eip712: { name: 'United Stables', version: '1' },
})

// 4. Retry with the credential — the server verifies, b402 broadcasts.
const paid = await fetch(url, { headers: { Authorization: credential } })
if (paid.status !== 200) {
  // The body carries the verifier's reason (e.g. a b402 /settle errorReason).
  throw new Error(`payment rejected (${paid.status}): ${await paid.text()}`)
}
console.log('paid ✓', await paid.json())
const receipt = deserializeEvmReceipt(paid.headers.get('Payment-Receipt')!)
console.log(`settle tx (broadcast by b402): https://bscscan.com/tx/${receipt.reference}`)
```

**Browser wallets (MetaMask etc.):** identical flow — pass an `account`
whose `signTypedData` delegates to the wallet instead of
`privateKeyToAccount` (see `walletSignerFor` in
[`examples/client/src/actions/shared.tsx`](../examples/client/src/actions/shared.tsx));
the demo client's **Authorization** tab is exactly this buyer running against
MetaMask.

Or skip writing the buyer and pay with the bundled demo pair:

```bash
# examples/server/.env: the same values as above
pnpm --filter @bnb-chain/mpp-example-server start    # mode 3 banner confirms b402
pnpm --filter @bnb-chain/mpp-example-client dev      # Authorization tab → Run All
```

## Five rules

1. **`recipient` must be your registered b402 payout** for the chosen chain.
   An unregistered payout boots fine and fails at the **first paid request**
   (a `/settle` `errorReason` the buyer sees as a 402).
2. **`B402_CHAIN` is explicit and `bsc` is the only working eip3009 chain**
   (testnet: see the warning up top). Real funds — start with a small price.
3. **The RSA key is the onboarding PKCS#8 key, not an EVM key.** Every b402
   call is RSA-signed (`X-Tesla-*` headers); `clientId` + `accessToken` alone
   cannot sign. A malformed key fails at boot with a format hint.
4. **Token identity = EIP-712 domain, not ticker.** b402 matches the token by
   its on-chain `name()` + version — `United Stables`/`1` for `$U` — and the
   SDK resolves this from the curated matrix automatically. A mismatch fails
   safe before settling.
5. **b402 is a trusted settlement oracle.** Your server still verifies the
   buyer's credential locally (challenge binding, signature, amount,
   recipient); only the broadcast is delegated. Core trusts b402's
   `success` + tx hash (cross-checking the echoed payer/network/amount
   against the signed authorization) and does not re-fetch the receipt. Need
   independent on-chain confirmation? Self-host the broadcast instead: drop
   `settleBackend` and pass a funded `settlementAccount`
   ([adr/0002](adr/0002-settle-adapter.md)).

## Standalone B402 Exact

Use this mode when the resource speaks the native x402 envelope: JSON `402`
body, `X-PAYMENT` request header, and `X-PAYMENT-RESPONSE` receipt header. The
extension advertises the configured methods that B402 actually supports for
the resolved token. `permit2-upto` is not part of the public payment path.

Merchant:

```ts
const b402 = createB402Extension({
  client,
  methods: ['eip3009', 'permit2-exact'],
})

const exact = b402.exact({
  resolvePayment: async (request) => {
    const invoiceId = new URL(request.url).searchParams.get('invoice')
    const invoice = await invoiceStore.requireOpen(invoiceId)
    return {
      network: invoice.network,
      asset: { address: invoice.token, name: invoice.eip712Name },
      payTo: invoice.payout,
      amount: invoice.atomicAmount,
      resource: { url: request.url, description: `invoice ${invoice.id}` },
    }
  },
  onSettlementUnknown: async (context) => {
    // Application-owned durability. Do not emit the reusable signature to normal logs.
    await reconciliationStore.record(context)
  },
})

app.get('/x402/premium', async (c) => {
  const result = await exact(c.req.raw)
  if (!result.paid) return result.response
  return result.withPaymentResponse(c.json({ ...yourContent, paymentMethod: result.method }))
})
```

The Exact Module validates the complete buyer payload, pins all accepted
requirements, reconstructs the facilitator request from merchant-owned values,
and checks the successful settlement's transaction, amount, network, and
payer. `onSettlementUnknown` is an application integration hook, not an SDK
database: the SDK classifies uncertainty and returns the exact request; the
merchant decides how to persist and reconcile it.

Buyer:

```ts
import { B402Permit2ApprovalRequiredError, createB402PaymentClient } from '@bnb-chain/mpp/b402'
import { erc20Abi } from 'viem'

const buyer = createB402PaymentClient({
  account,
  methods: ['eip3009', 'permit2-exact'],
  trustedSpenders: { 'eip155:56': [AUDITED_B402_EXACT_PROXY] },
  permit2Allowance: ({ owner, token, spender }) =>
    publicClient.readContract({
      address: token,
      abi: erc20Abi,
      functionName: 'allowance',
      args: [owner, spender],
    }),
})

try {
  const result = await buyer.pay('https://merchant.example/x402/premium')
  const data = await result.response.json()
} catch (error) {
  if (!(error instanceof B402Permit2ApprovalRequiredError)) throw error
  // Ask the wallet owner to explicitly approve `error.approval.spender`,
  // wait for that transaction, then call buyer.pay() again.
}
```

EIP-3009 is sign-only. Permit2 Exact additionally requires a one-time ERC-20
approval to canonical Permit2 and a trusted B402 proxy spender. The high-level
client checks allowance before signing and never broadcasts an approval
silently. Low-level `buildEip3009Payment` and `buildPermit2ExactPayment`
constructors remain available for wallets that manage the HTTP loop themselves.

The old fixed/dynamic Permit2 Gate names remain source-compatible wrappers over
the shared Exact Module. New integrations should use `b402.exact()`.

## Package map

| Import                       | Runtime        | What                                                                                              |
| ---------------------------- | -------------- | ------------------------------------------------------------------------------------------------- |
| `@bnb-chain/mpp/b402`        | browser + Node | B402 Exact buyer client, low-level x402 codecs/signers, spender policy and result errors          |
| `@bnb-chain/mpp/b402/server` | Node           | RSA `B402Client`, shared `/supported` cache, Exact merchant handler; legacy Permit2 Gate wrappers |
| `@bnb-chain/mpp/b402/mppx`   | Node (core)    | `createB402Extension`, MPP authorization settlement adapter and compatibility `b402ChargeParams`  |

`@bnb-chain/mpp/b402` is browser-safe so wallets can sign client-side; the
credentialed `B402Client` stays server-side (it holds your RSA key). Deeper
reference: the JSDoc on each export, [adr/0002](adr/0002-settle-adapter.md)
(settle-backend seam + trust model), [adr/0004](adr/0004-b402-permit2.md)
(Permit2 wire spec + security model).
