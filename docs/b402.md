# b402 — Binance OnchainPay (x402) integration

`@bnb-chain/mpp` ships first-class support for **b402**, the
[Binance OnchainPay](https://developers.binance.com/docs/onchainpay-x402/introduction)
gateway — an **x402 v2** facilitator (`/supported` · `/verify` · `/settle`).

> b402 is **x402, not mppx**. It is a different HTTP envelope from this SDK's
> `draft-evm-charge-00` charge flow, layered alongside it — see
> [architecture.md](architecture.md#b402-x402-facilitator). The only shared code
> is the EIP-712 primitive (`src/protocol/TypedData.ts`): the EIP-3009 credential
> is byte-identical on both sides (b402 just uses a random nonce instead of the
> mppx `challengeHash`).

## Packages

| Import                       | Runtime        | Depends on core? | What                                                                                                                                                                       |
| ---------------------------- | -------------- | ---------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `@bnb-chain/mpp/b402`        | browser + Node | no               | x402 v2 types; `X-PAYMENT` / `X-PAYMENT-RESPONSE` codecs; `buildEip3009Payment`; `recoverEip3009Payer`; `isEip3009PaymentPayload`; `randomB402Nonce`; `chainIdFromNetwork` |
| `@bnb-chain/mpp/b402/server` | Node only      | no               | `B402Client` (RSA "Tesla" request signing → `/supported` · `/verify` · `/settle`); `signTeslaRequest` / `verifyTeslaSignature` / `loadRsaPrivateKey`                       |
| `@bnb-chain/mpp/b402/mppx`   | Node only      | **yes**          | `B402Adapter` — the mppx bridge: implements the core `SettleAdapter` seam so a charge flow settles its EIP-3009 `authorization` via b402                                   |

`@bnb-chain/mpp/b402` is browser-safe (viem + Web Crypto only) so a wallet can
sign the payment in the browser. The credentialed `B402Client` stays server-side
because it holds the merchant's RSA key — never ship it to the client. Only the
`mppx` subpath pulls in `@bnb-chain/mpp/server`; the wire + client subpaths stay
core-free, so a standalone x402 integration never loads the charge engine.

## Two ways to use it

1. **Standalone x402 gateway** — your endpoint speaks x402 v2 to buyers and
   calls `B402Client` for `/verify` + `/settle` (the [Flow](#flow) below). The
   `@bnb-chain/mpp/b402` primitives give you the codecs + payload builders; no
   bundled demo for this path (the mppx-backend demos cover the wired flow).
2. **As an mppx settlement backend** — keep this SDK's mppx charge wire for
   buyers and delegate just the EIP-3009 settlement to b402 via
   `B402Adapter` (`@bnb-chain/mpp/b402/mppx`):

   ```ts
   import { B402Adapter } from '@bnb-chain/mpp/b402/mppx'
   import { B402Client } from '@bnb-chain/mpp/b402/server'
   import { chargeAsync } from '@bnb-chain/mpp/server'

   const charge = await chargeAsync({
     chain: 'bsc',
     token: 'U',
     recipient: B402_REGISTERED_PAYOUT, // must be your b402 payout
     challengeBinding: { mode: 'mppx-managed' },
     credentialTypes: ['authorization'], // b402 covers auth; no local signer for permit2
     settleBackend: new B402Adapter(new B402Client({ baseUrl, clientId, accessToken, privateKey })),
     // no settlementAccount — b402 broadcasts + pays gas
   })
   ```

   Buyers are unaffected (same mppx `Authorization: Payment` credential, same
   `Payment-Receipt`); only the settle step changes.

   **Trust model:** b402 is a trusted settlement _oracle_ here — core trusts its
   `success` + tx hash and does NOT re-fetch the receipt or wait
   `confirmations` on this path. Before issuing the receipt the verifier asserts
   the transfer b402 _reports_ (payer / network / amount) equals the signed
   authorization — an auxiliary check that catches b402 settling a _different_
   transfer, not a fabricated `success`. A `success` missing an amount is treated
   as pending (retryable), never a receipt. If you need core to confirm
   settlement on-chain itself, use `LocalSignerAdapter` instead. See
   [adr/0002-settle-adapter.md](adr/0002-settle-adapter.md). eip3009 only — the
   `recipient` must be your registered b402 payout.

### Bazaar discovery metadata (opt-in)

b402 persists an optional **Bazaar** blob you attach to `/settle` for the
upcoming public discovery layer. Pass it once via `B402Adapter`; it rides on
`paymentPayload.extensions.bazaar`. An invalid / unpersisted blob is skipped by
the indexer and **never fails the settle**, so it's safe to ship before the
registry launches.

```ts
new B402Adapter(client, {
  bazaar: {
    info: { input: { type: 'http', method: 'GET', path: '/api/premium' } },
    schema: { $schema: 'https://json-schema.org/draft/2020-12/schema', type: 'object' },
    description: 'BNB Chain stablecoin market snapshot (premium)',
    // routeTemplate: '/users/:userId',   // for parameterized routes
  },
})
```

The blob describes the resource being charged, so set it per resource/route.
See the [b402 Bazaar docs](https://developers.binance.com/en/docs/products/onchainpay-x402/b402-bazaar).

> **Future direction (design-only).** A unified multi-rail layer — one buyer
> `pay(url, { policy })` and one merchant `createPaymentGateway({ adapters, resources })`
> that negotiates across the mpp and x402/b402 wires — is designed in
> [adr/0003-payment-offer-layer.md](adr/0003-payment-offer-layer.md). It is NOT implemented;
> today you wire b402 explicitly via the two ways above.

## Flow

```
buyer / wallet ──GET──► merchant ──RSA-signed──► b402 gateway ──► BSC
  no X-PAYMENT   → 402 + accepts[]  (extra echoed from /supported)
  X-PAYMENT       → /verify → /settle → 200 + content + X-PAYMENT-RESPONSE
```

1. The merchant fetches `/supported` (cache it), then echoes the matching
   `kinds[].extra` verbatim into the `402` response's `accepts[]`.
2. The buyer signs an EIP-3009 `TransferWithAuthorization` (`buildEip3009Payment`)
   — no gas, no approval — and resends it as a base64 `X-PAYMENT` header.
3. The merchant calls `/verify` then `/settle`; b402 sponsors gas and moves funds
   buyer → merchant on-chain, returning the tx hash in `X-PAYMENT-RESPONSE`.

## API version

`B402Client` targets **Open APIs v2** (`/papi/v2/b402/*`, `x402Version: 2`). V1
(`/papi/v1/b402/*`) is legacy and not supported — v2 replaced the top-level
`scheme`/`network` with `paymentPayload.accepted`, split `facilitatorAddress`
into `signerAddress` + `spenderAddress`, and uses CAIP-2 wildcard `signers` keys.

## Run the demos

b402 is demoed as an **mppx settlement backend** (usage #2 above) — the buyer
speaks the SDK's mppx wire, the merchant settles the EIP-3009 `authorization`
via b402. Two existing examples cover the two sides:

| Example                                      | Role                                                                                                                                                                                              |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| [`merchant-demo`](../examples/merchant-demo) | server side. Mode 3 (set the `B402_*` env) settles `authorization` on `bsc-testnet`/`$U` via `B402Adapter` — b402 broadcasts + pays gas. `RECIPIENT_ADDRESS` must be your registered b402 payout. |
| [`charge-demo`](../examples/charge-demo)     | browser wallet (the b402 buyer). Select **BSC Testnet ($U)** to switch to the EIP-3009 `authorization` path: connect MetaMask, sign `transferWithAuthorization` (no gas), submit.                 |

```bash
# 1. server — mode 3 (b402 settle). Fill examples/merchant-demo/.env first:
#    RECIPIENT_ADDRESS (your b402 payout) + MPP_SECRET_KEY + B402_BASE_URL
#    (https://qacb.sdtaop.com) / B402_CLIENT_ID / B402_ACCESS_TOKEN / B402_PRIVATE_KEY.
pnpm --filter @bnb-chain/mpp-example-merchant-demo start

# 2. web wallet — point its endpoint at the merchant, pick "BSC Testnet ($U)",
#    connect MetaMask, and sign + submit the EIP-3009 authorization.
pnpm --filter @bnb-chain/mpp-example-charge-demo dev
```

> Runs on **BSC Testnet** (`eip155:97`, no real funds). The buyer signs an
> EIP-3009 authorization (no gas, no broadcast on the buyer side); only the
> merchant's b402 settle broadcasts it. A headless CLI buyer also lives in
> [`client-demo`](../examples/client-demo).

## Gotchas

- **RSA key required for live calls.** Every request to b402 is RSA-signed
  (`X-Tesla-Signature`); a live call needs the merchant's registered PKCS#8 key
  (`B402_PRIVATE_KEY`, accepts Base64-DER / Base64-PEM / raw PEM). The `clientId`
  and `accessToken` alone cannot sign.
- **Token name ≠ ticker.** `B402Adapter` resolves the `/supported` kind by the
  token's on-chain EIP-712 `name()` + `version` (`Eip3009Settlement.eip712`), NOT
  the symbol — `United Stables` (not `U`) for `$U`, `World Liberty Financial USD`
  for USD1. A wrong name/version means `/supported` has no matching eip3009 kind
  and the adapter throws before settling.
- **`$U` lives at different addresses per network.** Curated eip3009 pairs:
  `('bsc', 'U')` at `0xcE24…6666` (mainnet, real funds) and `('bsc-testnet', 'U')`
  at `0x180B…6A49` (testnet, the b402 demo token). The non-EIP-3009 testnet
  sibling `0x2Ae9…0a66` is deliberately NOT in the matrix. See
  `src/server/curated.ts`.
- **eip3009 only** (this SDK's `authorization` settle path): `$U` / USD1.
  Permit2 tokens (USDT / USDC) are **not modeled** — `PaymentPayload` only
  expresses the EIP-3009 `ExactEvmPayload`, so `B402Client` cannot build or
  forward a Permit2 payment. Supporting it would need a Permit2 `PaymentPayload`
  variant (a future addition).
