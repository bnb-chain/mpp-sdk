# B402 provider extension

`@bnb-chain/mpp` integrates B402 as an extension to `mppx`. The SDK does not
implement a facilitator, replace MPP transport, or own merchant order state.

Two Interfaces are available:

| Interface                 | Settlement methods                | Use when                                                                           |
| ------------------------- | --------------------------------- | ---------------------------------------------------------------------------------- |
| MPP-native `b402/charge`  | B402 EIP-3009, B402 Permit2 Exact | The buyer and merchant use this package and need the complete B402 capability set. |
| `createB402Facilitator()` | EIP-3009 only                     | Existing code already uses the standard `mppx` `evm/charge` x402 facilitator Seam. |

Permit2 Upto is not supported. B402 Permit2 Exact cannot be translated into
the standard `evm/charge` Permit2 credential because the spender and witness
contracts differ.

## Package entry points

| Entry point                  | Runtime        | Purpose                                                                                                                               |
| ---------------------------- | -------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| `@bnb-chain/mpp/b402`        | browser/server | Shared Method, wire types, and low-level signing primitives.                                                                          |
| `@bnb-chain/mpp/b402/client` | browser/server | `b402.charge()` wallet Implementation and Permit2 allowance contract.                                                                 |
| `@bnb-chain/mpp/b402/server` | Node           | `b402.charge()`, RSA-authenticated `B402Client`, `/supported` cache, settlement classification, and the standard facilitator Adapter. |

## Merchant: MPP-native B402 charge

```ts
import { B402Client, b402 } from '@bnb-chain/mpp/b402/server'
import { Mppx } from 'mppx/server'

const client = B402Client.fromEnv()
if (!client) throw new Error('B402 is not configured')

const method = await b402.charge({
  client,
  network: 'eip155:56',
  currency: {
    address: '0xYourToken',
    decimals: 18,
    // EIP-712 domain values, not the ticker symbol.
    name: 'Token Domain Name',
    version: '1',
  },
  recipient: '0xYourRegisteredPayout',
  onSettlementUnknown(event) {
    // Hand off to your order/reconciliation system. Persist the exact request
    // only if your operational policy requires it.
    queueForReconciliation(event)
  },
})

const payments = Mppx.create({
  methods: [method],
  secretKey: process.env.MPP_SECRET_KEY!,
})

// One route can select either supported proof explicitly.
const eip3009Route = payments.b402.charge({
  amount: '0.01', // display units; the Method normalizes with currency.decimals
  transferMethod: 'eip3009',
})

const permit2Route = payments.b402.charge({
  amount: '0.01',
  transferMethod: 'permit2-exact',
})
```

Use the returned route exactly like any other `mppx` HTTP method:

```ts
const result = await permit2Route(request)
if (result.status === 402) return result.challenge
return result.withReceipt(new Response('paid content'))
```

The merchant owns the economic configuration. `/supported` supplies only the
current B402 signer and, for Permit2 Exact, proxy spender. That snapshot is
included in the HMAC-bound MPP Challenge and reused on the paid retry.
`b402.charge()` is asynchronous because it validates the configured transfer
methods against `/supported` before the HTTP server starts accepting traffic.
Set `transferMethods: ['eip3009']` or `['permit2-exact']` when a deployment
intentionally exposes only one path; the default requires both capabilities.

## Buyer: one payment-aware fetch

```ts
import { b402, CURATED_B402_SPENDERS } from '@bnb-chain/mpp/b402/client'
import { Mppx } from 'mppx/client'

const method = b402.charge({
  account: walletAccount,
  allowedNetworks: ['eip155:56'],
  allowedCurrencies: [{ network: 'eip155:56', address: '0xYourToken' }],
  maxAmount: '1',

  // Permit2 Exact only. This reads ERC-20 allowance(owner, canonical Permit2).
  permit2Allowance: ({ owner, token, spender }) =>
    publicClient.readContract({
      abi: erc20Abi,
      address: token,
      functionName: 'allowance',
      args: [owner, spender],
    }),

  // Required trust anchor: never trust spenderAddress merely because it
  // appeared in an HTTP 402 response.
  trustedSpenders: {
    'eip155:56': [CURATED_B402_SPENDERS['eip155:56']!.exact],
  },
})

const payments = Mppx.create({
  methods: [method],
  orderChallenges: method.prefer(['permit2-exact', 'eip3009'], {
    onMissingAllowance: 'fallback',
  }),
  polyfill: false,
})

const response = await payments.fetch('https://merchant.example/resource')
```

The SDK never sends an approval transaction. If Permit2 is selected without
sufficient allowance, credential creation raises
`B402Permit2ApprovalRequiredError`; the application decides whether and how to
request `approve(canonicalPermit2, amount)` from the user.

For MPP-native credentials, both EIP-3009 and Permit2 unordered nonces are
derived from `keccak256(challenge.id || challenge.realm)`. A proof cannot be
re-attached to a different MPP Challenge with otherwise identical payment
terms.

## Standard `mppx` EIP-3009 compatibility

Existing standard EVM integrations can use B402 as their x402 facilitator:

```ts
import { B402Client, createB402Facilitator } from '@bnb-chain/mpp/b402/server'
import { evm, Mppx } from 'mppx/server'

const client = B402Client.fromEnv()!
const method = evm.charge({
  chainId: 56,
  currency: '0xYourEip3009Token',
  decimals: 18,
  authorization: { name: 'Token Domain Name', version: '1' },
  recipient: '0xYourRegisteredPayout',
  x402: {
    facilitator: createB402Facilitator({
      client,
      onSettlementUnknown: queueForReconciliation,
    }),
  },
})

const payments = Mppx.create({
  methods: [method],
  secretKey: process.env.MPP_SECRET_KEY!,
})
```

This Adapter is deliberately EIP-3009-only. Use `b402/charge` for B402
Permit2 Exact.

## Verification and settlement invariants

Before `/verify`, the MPP-native server Implementation:

- verifies the server-issued Challenge through `mppx`;
- pins amount, token, network, recipient, method, EIP-712 domain, B402 signer,
  and B402 spender;
- validates time bounds and Challenge-derived nonce;
- recovers the EIP-712 signer locally;
- reconstructs `accepted` and the signed payload from authoritative values;
- never forwards buyer-provided extensions or resource metadata.

`/verify` rejection is side-effect-free. `/settle` has three outcomes:

- verified success: transaction hash, amount, network, and payer all match;
- definitive rejection: B402 returned `success: false` and an empty
  `transaction`, proving no transaction was broadcast;
- unknown: B402 returned `success: false` with any transaction evidence, a
  transport/response failure occurred after settle began, or the success
  response was malformed or mismatched.

Unknown settlement raises `B402SettlementUnknownError` and invokes the
configured callback. The SDK owns no database and does not decide whether to
fulfill, retry, refund, or reconcile an order.

The callback event contains the exact signed provider request. If the host
chooses to persist it, treat it as sensitive and replayable until its deadline:
encrypt it at rest, restrict access, and apply the host's retention policy.

Successful receipts preserve `challengeId`, `externalId` (when configured),
`network`, `payer`, and `transferMethod` as method-specific fields. The host
must still make fulfillment idempotent by its own order/external ID; the SDK
does not turn a paid HTTP handler into an order system.

## B402 credentials

`B402Client.fromEnv()` reads these variables as an all-or-nothing group:

```text
B402_BASE_URL
B402_CLIENT_ID
B402_ACCESS_TOKEN
B402_PRIVATE_KEY        # RSA PKCS#8/PEM issued during onboarding
```

The key is an RSA merchant request-signing key, not an EVM private key.
`B402SupportedCache` caches `/supported` with a bounded TTL and coalesces
concurrent refreshes; pass one cache to multiple method instances when they
should share the same provider snapshot.
