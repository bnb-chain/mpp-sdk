# ADR 0004 — b402 `permit2-exact` payments on the x402 wire

- **Status:** Accepted for `permit2-exact` — IMPLEMENTED 2026-07-02
  (`src/b402/Permit2.ts`: `buildPermit2ExactPayment` / `recoverPermit2ExactPayer` /
  `isPermit2PaymentPayload` / `CURATED_B402_SPENDERS`; demos: the example
  server's `/x402/premium` route + the example client's `x402 · Permit2`
  browser tab). Merchant hardening now lives in the shared B402 Exact Module:
  `createB402ExactHandler` handles EIP-3009 and Permit2 Exact, while the
  fixed/dynamic Permit2 Gate names remain compatibility wrappers. It preserves
  full requirement pinning, runtime facilitator-response
  parsing, a TTL-bounded `/supported` cache, and structured settlement-unknown
  reconciliation. The wire spec below was resolved from the official b402
  "Permit2 Signing Guide" (captured 2026-07-02):
  domain `{name:'Permit2', chainId, verifyingContract}` (NO version), witness is
  exactly `Witness { address to; uint256 validAfter }`, payload field
  `permit2Authorization`, all numerics decimal strings on the wire.
  `permit2-upto` stays OUT OF SCOPE for this product. Extends
  [0002](0002-settle-adapter.md) and instantiates
  the standalone-x402 rail sketched as Phases 2-4 in
  [0003](0003-payment-offer-layer.md).
- **Scope:** Let a buyer pay a b402 (Binance OnchainPay, x402 v2) endpoint with a
  **Permit2** signature — b402 broadcasts and pays gas — for tokens that either lack
  EIP-3009 entirely (USDT/USDC) or whose EIP-3009 door doesn't match (see the testnet
  `$U` facts below). This is a **standalone x402-wire** feature (`X-PAYMENT` header),
  NOT a change to the mppx charge wire or to `B402Adapter`.

## Why this cannot ride the mppx wire (restating the XOR theorem)

A Permit2 `PermitWitnessTransferFrom` signature binds BOTH the `spender` (enforced
on-chain as `msg.sender`) and the `witness` struct:

- **mppx `permit2` credential**: spender = the merchant's settlement signer,
  witness = `PaymentWitness(bytes32 challengeHash,string externalId)`
  (`src/protocol/TypedData.ts`).
- **b402 permit2**: spender = b402's per-scheme proxy (`extra.spenderAddress`),
  witness = `Witness(address to,uint256 validAfter)`.

One signature cannot satisfy both. Therefore `B402Adapter` (the mppx settle backend)
stays **EIP-3009-only**, and b402 Permit2 lives on the x402 wire where the buyer signs
b402's shapes knowingly. This was decided in ADR-0002/0003 and is not reopened here.

## Design

### Wire model (`permit2-exact`)

The x402 payload is discriminated by
`accepted.extra.assetTransferMethod === 'permit2-exact'`:

```ts
export interface Permit2Authorization {
  readonly permitted: { readonly token: `0x${string}`; readonly amount: string }
  readonly from: `0x${string}`
  readonly spender: `0x${string}`
  readonly nonce: string
  readonly deadline: string
  readonly witness: { readonly to: `0x${string}`; readonly validAfter: string }
}
export interface Permit2EvmPayload {
  readonly signature: `0x${string}` // PermitWitnessTransferFrom EIP-712 sig
  readonly permit2Authorization: Permit2Authorization
}
```

All numeric values are decimal strings on the wire. The EIP-712 domain is the
canonical Permit2 contract with no `version`; the witness type string and field
order are fixed interop contracts in `src/protocol/TypedData.ts`.

### Buyer builder — `buildPermit2ExactPayment` (browser-safe, `@bnb-chain/mpp/b402`)

```ts
buildPermit2ExactPayment({
  account,                    // viem LocalAccount / wallet-backed signer
  requirements,               // the chosen permit2-exact accepts[] entry
  trustedSpenders,            // REQUIRED allowlist — see security model
  deadline?,                  // default now + maxTimeoutSeconds
})
```

### Security model (the reason this was gated)

The buyer **cannot** call `/supported` (it is RSA-credentialed, merchant-only), so the
402's `spenderAddress` / witness fields are attacker-controllable from the buyer's
seat. "Sign whatever the challenge declares" is a phishing primitive: a Permit2
signature to a hostile spender is a direct token-theft instrument. Hence, fail-closed
rules enforced by the builder:

1. **Spender allowlist — no default-trust.** `trustedSpenders` is a REQUIRED
   parameter; the builder refuses a `requirements.extra.spenderAddress` outside it.
   The SDK ships a **curated b402 spender table** (dated + per network).
   Permit2 Exact callers pass only `[CURATED_B402_SPENDERS[network].exact]`,
   or their own audited Exact proxy list — never the `upto` proxy, and never
   implicit trust.
2. **Known witness only.** The builder constructs exactly
   `Witness { to: requirements.payTo, validAfter }`; server-supplied witness
   blobs are never signed verbatim.
3. **Exact amount.** `permitted.amount` MUST equal `requirements.amount`; no
   ceiling or facilitator-selected settle amount exists on this path.
4. **Deadline cap.** `deadline ≤ now + maxTimeoutSeconds + 10min` slack; longer
   windows are refused (a long-dated permit is an off-protocol spend authorization).
5. **Validator parity.** `isEip3009PaymentPayload` stays; add
   `isPermit2PaymentPayload` with the same full-shape rigor (envelope, scheme/method
   discriminant, hex/decimal formats) for merchant-side gating of `X-PAYMENT`.

### Merchant side

The primary merchant surface is `createB402Extension().exact()`, backed by
`createB402ExactHandler`. It supports the two documented Exact transfer
methods without merging the MPP and x402 wires. The original Permit2-specific
surface remains source-compatible:

- `createPermit2ExactX402Gate` resolves one fixed requirement at creation.
- `createDynamicPermit2ExactX402Gate` resolves amount/asset/payout from the
  current request and uses a bounded `/supported` cache.
- `createX402Gate` is only a compatibility alias for the fixed Permit2 Exact
  gate; it is not a generic x402 scheme router.

All handlers select x402 v2 Exact kinds, echo the facilitator's
`extra` into the 402, validate the full payment shape, compare every accepted
requirement field, and reconstruct the payload from server-owned values before
the RSA-authenticated `/verify` and `/settle` calls. Successful facilitator
responses are runtime-parsed and cross-checked for tx hash, amount, network,
and payer.

The dynamic resolver must return the same immutable payment record for probe
and paid retry. `B402SupportedCache` is TTL-bounded and single-flight; the same
instance can be shared with `B402Adapter`. A settle transport failure or
incomplete/mismatched success produces `B402SettlementUnknown` (or the legacy
`X402SettlementUnknown` alias) and calls
`onSettlementUnknown` with the exact facilitator request. Deployments persist
that state securely and reconcile it on-chain; they do not treat it as unpaid.

### Runnable examples

- `examples/server`: `/x402/premium` uses `createB402Extension().exact()`, shares one
  `/supported` cache with the EIP-3009 adapter, and demonstrates the explicit
  settlement-unknown hook. Its in-memory recorder is development-only.
- `examples/client`: the `x402 · Permit2` tab performs the one-time Permit2
  approval, signs the exact b402 witness, and pays through `X-PAYMENT`.

## Explicit non-goals

- Bridging mppx `permit2` credentials to b402 (impossible — XOR theorem above).
- Auto-selecting between mpp and x402 rails in `pay()` (that is ADR-0003 Phase 2/3,
  gated on the `PaymentIntentStore`).
- `permit2-upto` in any form. It is not modeled, built, gated, verified, or
  settled by this SDK.
